# 任务解阻：手机回答、续办、复盘

电脑上的 coding agent（经 picoclaw-relay 中继）执行任务时遇到选型或缺少信息会停下来等
回答。你在手机上替用户完成「看到问题 → 回答 → 等它跑完 → 收结果」的循环，
不用守着电脑。

## 工具前置

| 动作 | server | 说明 |
|---|---|---|
| 查待答问题、提交回答、查任务状态 | picoclaw-relay | 以 `minis-mcp-cli tools picoclaw-relay` 实际列表为准：列出待答问题、提交回答、查任务状态三类语义的工具 |
| 任务关联 | larry-todo | list_todos / update_todo / add_todo |
| 复盘草稿 | memos | 创建笔记类工具，以 tools 列表为准 |

picoclaw-relay 未注册或不可达时：告知用户「中继没接入」，不要猜问题内容。
问题与回答的轮询触发、断线恢复由 relay 与电脑侧负责；你只处理当前时刻拿到的状态。

## 流程

### 1. 列出问题卡

查询待答问题，逐条展示：任务标识（任务名/ID）、问题全文、已等多久、附带上下文
摘要。多条时按等待时间排序，标出「第几条」。同时说明每条属于哪个电脑会话，
避免把 A 任务的答案发给 B 任务。

### 2. 收集回答

用户口述回答后，**复述一遍要点再提交**。三类回答要额外确认：

- 选型类：答完后补一句「选这个的理由」让用户看过再发。
- 不可逆操作（删除、发布、覆盖）：原文引用操作对象，明确得到「确认」才提交。
- 涉及密钥、凭证、账号、隐私的回答：**不提交**。当前中继走公网明文 HTTP，
  提醒用户这类信息不要经中继发送，等可信 HTTPS 或当面处理。

### 3. 提交并续办

提交回答后查任务状态：继续跑就告知「已提交，任务继续」并结束本轮；
立刻又卡住就回到第 1 步。用户问「跑完了吗」时直接查状态再答，不要编造进度。

问题卡带 LarryTodo 任务 ID 时，提交后把「已回答〈摘要〉」追加到对应待办备注
（update_todo 全量清空未传字段，传参要带全原内容）。

### 4. 任务完成回报

任务状态变为完成后，回报三样：**产物**（文件/提交/链接）、**验证结果**
（agent 自测输出摘要）、**待验收事项**（需要用户人工确认什么）。AI 报告的
「完成」不等于验收通过，回报里要分开说。

### 5. 复盘草稿（用户说「复盘一下」时）

把这次任务整理成草稿，先展示再写入：

```
目标：〈当初要做什么〉
结果：〈AI 报告的结果，含产物链接〉
验收：〈用户已验收 / 待验收：…〉
遗留：〈没做完的、发现的坑〉
```

「AI 执行结束」与「用户验收完成」是两条记录：任务跑完只写「结果」，用户明确
认可后才在「验收」栏写「已验收」。用户认可草稿后写入 memos（草稿态，不发布）；
草稿里「有用的下一步」问一句「要转成待办吗」，同意则 add_todo 并把待办
recordId 回填到草稿里。

## 边界

- 不代用户做选型：用户问「你觉得选哪个」时给出建议与理由，但标明「由你拍板」，
  等确认再提交。
- 续办轮询超过 10 分钟仍无进展时，停止等待并告知当前状态与下次查看建议，
  不要无限循环刷状态。
